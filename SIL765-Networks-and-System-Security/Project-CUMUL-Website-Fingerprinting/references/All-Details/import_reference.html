Lazy & Conditional Imports special patterns
Import pattern Where File Why lazy / conditional
try: import scapy Module-level try/except capture.py Sets SCAPY_AVAILABLE flag. If Scapy/Npcap is missing, capture falls back to browser-only mode without crashing the entire application. All sniff/wrpcap calls are guarded by this flag.
try: from stem import Signal Module-level try/except capture.py Sets STEM_AVAILABLE flag. If Stem is missing, Tor circuit rotation falls back to a 5 s sleep. Bootstrap detection falls back to a fixed delay. Stem is optional for basic operation.
try: import undetected_chromedriver Module-level try/except capture.py Sets UNDETECTED_AVAILABLE flag. If undetected-chromedriver is absent, create_driver() silently falls back to standard Selenium Chrome. Bot detection may be less effective in fallback mode.
try: import fasteners Module-level try/except capture.py Sets FASTENERS_AVAILABLE flag. Falls back to threading.Lock() if fasteners is absent. The thread-lock fallback works correctly in single-process mode but cannot protect across separate OS processes.
try: import psutil Module-level try/except capture.py Sets PSUTIL_AVAILABLE flag. _kill_child_processes() is a no-op if psutil is absent. Chrome zombie cleanup is skipped rather than crashing.
import matplotlib
import matplotlib.pyplot as plt		 Inside each plot function body graphs.py visualize.py Matplotlib has a slow startup (~0.5 s) and must have its backend set to "Agg" before the first import. Lazy importing inside each function ensures matplotlib.use("Agg") is always called first, and avoids the overhead in modules that only train without plotting.
from features.cumul import build_feature_vector Inside _extract_feature_sample() body data.py Imported inside the worker function body so this import (which triggers a Scapy import chain) only happens in the subprocess worker, not in the main training process. Prevents Npcap driver initialisation conflicts on Windows when spawning many processes.
from . import capture as cap_mod Inside _process_one_task() and collect_sites() collection_menu.py Same reason as above: capture.py imports Scapy at module level. Lazy import inside the worker function ensures the Scapy+Npcap driver stack is only initialised in child subprocesses, not in the parent orchestrator.
from .varcnn.model import ... Inside if-branch inside run() train.py test.py TensorFlow is very heavy (~2 s startup, ~1 GB RAM). It is imported only when the user explicitly selects var-CNN. SVM-only runs incur zero TensorFlow overhead.
import numpy as np Inside function bodies in some modules data.py evaluate.py visualize.py In modules where numpy is only needed in specific code paths (e.g. only when features are actually extracted), numpy is imported locally rather than at module top to keep the import chain lighter for modules that may be imported for non-numerical tasks.
